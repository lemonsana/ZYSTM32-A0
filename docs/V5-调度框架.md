# V5 调度框架说明

> 适用工程：ZYSTM32-A0（STM32F103RCT6，72MHz）
> 涉及源码：`SYSTEM/sched/`（调度内核）、`SYSTEM/app/`（模式表）、`USER/main.c`（注册）
> 引入版本：V5
> 控制算法与参数：**与 R1.1 完全一致，本次只动架构**

---

## 1. 为什么改

R1.1 的主循环是：

```c
while (1)
{
    KeyScanTask();
    ModeTask();
    Debug_Task();
    delay_ms(10);       /* ← 节拍 = 10ms + 所有任务的耗时 */
}
```

问题不在功能，而在**节拍不可信**：

| 场景 | 实际周期 | 后果 |
|---|---|---|
| 正常循迹 | 10ms + 任务耗时 | 基准一开始就不准 |
| 融合模式测距（`AVoid_Measure()` 最长 30ms） | 约 40ms | 一次丢 3 拍 |
| 串口打印一行（约 100 字符 @115200 ≈ 9ms） | 约 20ms | 每 200ms 抖一次 |

而 `GRAY_FRAME_MS = 10`、PID 的 D 项、丢线 3000ms 计时，全都是按"每拍正好 10ms"写的。
节拍一抖，**微分项和超时判定就跟着错，而且现场完全看不出来**——只会觉得"这车有时候怪怪的"。

V5 把节拍交给硬件：TIM6 每 5ms 打一拍，任务各自按注册周期执行，
控制周期不再被别的任务带偏。

---

## 2. 现在的结构

```text
TIM6 中断 (5ms)                         主循环
┌──────────────────────────┐      ┌───────────────────────────┐
│ g_tick_ms += 5           │      │ __WFI() 睡眠               │
│ 遍历任务表                │ flag │ 唤醒 → 跑所有到期的后台任务 │
│ 前台任务：直接执行         │ ───► │ 回到 __WFI()               │
│ 后台任务：只置 flag        │      └───────────────────────────┘
└──────────────────────────┘
```

```c
int main(void)
{
    /* ... 各模块初始化 ... */

    Sched_Init();                                       /* TIM6 配好，先不启动 */
    Sched_Register(app_mode_key_task, 5);               /* 前台 */
    Sched_RegisterDeferred(app_mode_task, MODE_TASK_MS);/* 后台 10ms */
    Sched_RegisterDeferred(app_mode_debug_task, 200);   /* 后台 200ms */
    app_mode_start(0);
    Sched_Start();

    while (1) Sched_Run();
}
```

## 3. 两类任务

| 接口 | 执行位置 | 适合放什么 | 硬性要求 |
|---|---|---|---|
| `Sched_Register(func, period)` | TIM6 中断里 | 读 IO、置标志、极短的状态机 | 单次 < 100µs，**禁止** delay / printf / 等硬件 |
| `Sched_RegisterDeferred(func, period)` | 主循环 | 测距、串口、I2C、控制计算 | 单次耗时 < 自己的周期 |

规则：
1. 所有周期必须是 `SYS_TICK_MS`（5ms）的整数倍；
2. 后台任务超时不会崩，但会挤压后面的任务——用自己的周期去核对。

## 4. 加一个任务 / 加一个模式

### 加周期任务

```c
/* 在 main.c 里加一行即可，周期必须是 5 的倍数 */
Sched_RegisterDeferred(my_task, 50);
```

### 加业务模式

`SYSTEM/app/app_mode.c` 里加一行，**不用改 switch、不用改按键逻辑**：

```c
static const app_mode_desc_t g_modes[] =
{
    { '1', "T1 循迹+避障", mode1_start, mode1_update, mode1_stop },
    { '2', "T2 纯避障",    mode2_start, mode2_update, mode2_stop },
    { '3', "T3 纯循迹",    mode3_start, mode3_update, mode3_stop },
    /* { '4', "T4 ...", mode4_start, mode4_update, mode4_stop }, */
};
```

按键轮换、串口字符、调试打印的 `mode=` 字段会自动跟着表走。

`update()` 返回 `APP_TASK_DONE` 表示这个模式要收尾（自动停车 + 清积分 + 回到无模式状态），
适合做"往前走 50cm 就结束"这类一次性动作。

## 5. 怎么看节拍有没有被拖垮

调试行每 1 秒会多打一行：

```text
[sched] loop= 320us max=31200us
```

| 字段 | 含义 | 正常值 |
|---|---|---|
| `loop` | 上一轮后台处理耗时 | 循迹时几百 µs |
| `max` | 最近 1 秒内最坏一次 | 应该 < 10000，若经常 >15000 说明有任务在阻塞 |

`max` 稳定在 30000 以上 → 基本可以确定是融合模式里的 `AVoid_Measure()` 在阻塞（它最长等 30ms 回波）。
这不影响节拍基准（`g_tick_ms` 由硬件保证），但会让那一拍的控制输出"迟到"，
后续如果要彻底消除，需要把测距改成"启动 + 查询完成"的非阻塞状态机。

## 6. 迁移注意

1. **`delay_ms()` 照常可用**：SysTick 没动，仍然是 `delay.c` 在管；
2. **定时器占用**（V5）：

| 定时器 | 用途 | 备注 |
|---|---|---|
| TIM2 | 超声波 1MHz 计数 | 不动 |
| TIM3 | 舵机 50Hz (PB0/CH3) | 不动 |
| TIM4 | 电机 PWM 10kHz | 不动 |
| TIM5 | 红外遥控输入捕获 | 不动 |
| **TIM6** | **5ms 系统节拍** | V5 新增，基本定时器无引脚 |
| TIM7 | 空闲 | 备选节拍源 |
| SysTick | `delay_us` / `delay_ms` | 轮询模式，未开中断 |

3. **中断优先级**：TIM6 = 2，EXTI1（超声波回波）= 1，USART1 = 3；
4. **`g_tick_ms` 的类型是 `u32`**，49 天回绕，做差值比较不受影响。

---

## 7. 串口指令（V5 新增）

| 发送 | 动作 | 回复 |
|---|---|---|
| `1` / `2` / `3` | 切到对应模式（最后一个字符生效） | `T1` / `T2` / `T3` |
| 大小写 | 不敏感（`a` 等同 `A`） | — |

行结束符支持 `\r\n`，也兼容只发 `\n` 的工具。
串口指令和板载按键走的是同一套模式表，不会出现"两条路径行为不一致"。
